# LAMA — CONTAINER dependency set.
#
# Target: python:3.11-slim-bookworm / linux (see Dockerfile). For local
# macOS dev on Python 3.14 use `requirements-dev-macos.txt` instead.
#
# ── Why this file looks different from before ───────────────────────
# Until 2026-09 this was a raw `pip freeze` taken on a Linux CUDA
# workstation: 176 pins, of which an AST walk over all 91 backend
# application modules showed the code imports 30. The rest were that
# workstation's environment, not LAMA's dependencies. Notably it pinned
# 19 nvidia-*/cuda-*/triton packages -- multiple gigabytes of GPU
# runtime -- into an image whose own Dockerfile installs CPU-only torch
# from the CPU index specifically to avoid them. Those lines were also
# redundant: torch declares its own CUDA deps, so pre-installing the CPU
# build (Dockerfile:193) is what actually keeps them out, not this file.
#
# It also pinned packages with no code path at all: openai (LAMA calls
# every provider through raw httpx per CLAUDE.md contract #4 -- the only
# "openai" strings in the tree are provider names and base URLs),
# litellm, stripe, pandas, jq, s5cmd, the eight google-* SDKs (Gemini is
# reached via its OpenAI-compatible endpoint over httpx), and the dev
# tooling black/mypy/flake8/isort which the image never runs.
#
# This file now lists DIRECT dependencies only and lets pip resolve the
# transitive closure -- so numpy, scipy, scikit-learn, tokenizers,
# safetensors, huggingface-hub, lxml, aiohttp, regex, orjson and friends
# still get installed, by the packages that actually need them.
#
# To re-derive the direct set:
#   python -c "<AST walk over backend/**/*.py>"   # see docs/verification/
# To prove it resolves for the container:
#   pip install --dry-run --only-binary=:all: \
#       --python-version 3.11 --platform manylinux_2_28_x86_64 \
#       --target /tmp/probe -r backend/requirements.txt
# ════════════════════════════════════════════════════════════════════

# ── iter 13.90 — Pure-python Git client fallback ─────────────────────
# `_git_clone()` in routes/kb.py prefers the system `git` binary (faster,
# better cred helpers, shallow clones). If `git` is missing (slim runner
# images, local dev on a server without git, hardened k8s nodes) we fall
# back to `dulwich.porcelain.clone()` so the /api/kb/{pid}/clone-git
# endpoint still works. Adds ~600 KB and zero system deps.
# Pinned to 1.2.5+ which fixes CVE-2026-42305 (Windows arbitrary file
# write via NTFS-hostile tree entries, HIGH) and CVE-2026-47734
# (unbounded memory allocation in receive-pack, MEDIUM). Both are
# remote-attacker-controlled-input issues so the floor is mandatory.
dulwich>=1.2.5,<2.0
